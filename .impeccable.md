# PieCode Design Guidance

## Design Context

### Users
Solo developers using PieCode as a coding assistant while they inspect repositories, make focused edits, approve shell/tool actions, review diffs, and verify changes. They are often in flow and value low-friction controls, fast starts, and clear safety cues.

### Brand Personality
Helpful, fast, and trustworthy. The interface should feel like an assistant rather than an ops dashboard: calm, direct, and ready to help without hiding power-user capabilities.

### Aesthetic Direction
A refined dark developer workspace with warm industrial tones. Avoid generic AI neon gradients and heavy dashboard chrome. Prefer assistant-like prompts, visible next actions, compact command surfaces, and clear hierarchy for risky actions.

### Design Principles
1. Move fast by default: common actions should be one click or one command away.
2. Keep safety legible: approval flows should make consequences clear without slowing routine work.
3. Lead with assistant behavior: empty states, labels, and controls should suggest useful next steps.
4. Preserve expert density where it matters, but collapse empty or secondary information.
5. Accessibility is part of speed: keyboard and screen-reader flows should work predictably.
